# Scheduler 并行 Coding 任务设计方案

- 日期：2026-10-21
- 状态：阶段一已实施（2026-10-22）
- 适用范围：CodeGuild Development SubGraph
- 目标：允许 Scheduler 将同一批无依赖的就绪任务安全地分发给多个 Coding Worker 并行执行，并在隔离环境中完成确定性集成

## 1. 背景与当前结论

当前 Scheduler 已经能够根据任务 DAG 计算全部就绪任务，但执行阶段仍然是串行的：

1. `compute_ready_tasks()` 返回完整的就绪任务集合。
2. Scheduler 只把 `ordered_ready[0]` 写入唯一的 `active_task_id`。
3. Development SubGraph 沿 `scheduler → code_task → finalize_task → scheduler` 单路径循环。
4. Coding SubGraph 只读取一个 `active_task_id`。
5. 每个 Run 只有一个共享 worktree，尚未创建任务级隔离工作区。
6. RunManager 每个 Run 只保存一个挂起审批载荷，不能可靠处理多个 Coding Worker 同时产生的审批请求。

因此，现有实现具备 DAG 就绪判定能力，但不具备安全的并行 Coding 执行能力。

## 2. 设计目标

本次改造应满足以下目标：

- Scheduler 能一次分发多个互不依赖的 READY 任务。
- 并行数量受配置项限制，避免耗尽 LLM、CPU、内存和 Docker 资源。
- 每个 Coding Worker 使用独立 worktree 和任务分支，禁止共享写目录。
- 并行分支只返回任务级结果，不直接覆盖全局共享状态。
- Integration 节点按确定顺序将任务提交合并到 Run 分支。
- 单个任务失败不影响其他独立任务继续执行。
- 下游任务必须等待全部依赖成功集成后才能进入 READY。
- 合并冲突、验证失败、审批和服务重启均有明确的恢复语义。
- 保持现有串行模式兼容，可通过配置关闭并行执行。

## 3. 非目标

首期不处理以下能力：

- 跨 Run 的全局资源调度。
- 跨机器分布式 Coding Worker。
- 自动解决所有 Git 语义冲突。
- 根据历史吞吐量自动调整并发数。
- 对任意第三方工具建立分布式锁。

## 4. 总体架构

```text
                         ┌───────────────┐
                         │   Scheduler   │
                         └───────┬───────┘
                                 │ 计算 READY 集合并选择批次
                 ┌───────────────┼───────────────┐
                 │               │               │
                 ▼               ▼               ▼
          Coding Worker T1 Coding Worker T2 Coding Worker T3
          独立 worktree     独立 worktree     独立 worktree
          独立 task branch  独立 task branch  独立 task branch
                 │               │               │
                 └───────────────┼───────────────┘
                                 ▼
                       Integration Barrier
                                 │
                    按拓扑顺序集成任务提交
                                 │
                   ┌─────────────┴─────────────┐
                   │                           │
                   ▼                           ▼
             返回 Scheduler              全部任务完成
                                               │
                                               ▼
                                    Integration Test → Review
```

推荐使用 LangGraph 动态 fan-out/fan-in：Scheduler 根据本批任务返回多个动态分支，每个分支运行同一个 Coding Worker 子图，分支完成后通过 reducer 汇聚任务结果，再进入统一 Integration 节点。

## 5. Scheduler 调度策略

### 5.1 批次选择

Scheduler 保留现有的 DAG 校验、阻塞传播和拓扑排序逻辑，并将单任务选择改为批次选择：

```python
ready = compute_ready_tasks(tasks)
ordered_ready = [task_id for task_id in topological_order(tasks) if task_id in ready]
batch = select_parallel_batch(ordered_ready, tasks, settings.max_parallel_coders)
```

首期批次选择规则：

1. 只选择状态为 `READY` 的任务。
2. 最多选择 `max_parallel_coders` 个任务。
3. 按拓扑顺序和原有任务顺序保持确定性。
4. 明确存在文件范围重叠的任务不进入同一批次。
5. 未提供文件范围时允许并行，但由任务 worktree 和 Integration 负责最终冲突检测。

### 5.2 配置项

在 `Settings` 中新增：

```python
parallel_coding_enabled: bool = True
max_parallel_coders: int = 2
parallel_interactive_approval_enabled: bool = False
```

- `parallel_coding_enabled=false` 时保持当前串行行为。
- `max_parallel_coders` 建议默认值为 `2`，并限制为合理的正整数。
- 多审批队列完成前，interactive 模式默认降级为串行。

## 6. 状态模型

### 6.1 全局状态

当前单值字段 `active_task_id`、`scratch` 和 `validation` 不允许由并行分支共同写入。全局状态增加：

```python
current_tasks: list[str]
coding_results: Annotated[list[dict], task_result_reducer]
integration_results: list[dict]
active_batch_id: str
```

其中：

- `current_tasks` 表示当前批次所有活动任务。
- `coding_results` 只接收并行 Worker 的追加式输出。
- `integration_results` 由 Integration 节点统一写入。
- `active_batch_id` 用于恢复、追踪和防止上一批结果混入下一批。

### 6.2 Worker 输入

每个 Worker 接收隔离的任务上下文：

```python
{
    "run_id": "...",
    "batch_id": "...",
    "task_id": "T1",
    "workspace_path": "...-tasks/T1",
    "branch": "agent/run-12345678/task-T1"
}
```

### 6.3 Worker 输出

Worker 不直接更新全局 `task_dag`，只返回结构化结果：

```python
{
    "run_id": "...",
    "batch_id": "...",
    "task_id": "T1",
    "status": "done",
    "commit_sha": "...",
    "changed_files": [],
    "validation": {},
    "summary": "...",
    "error": ""
}
```

Reducer 必须按 `(batch_id, task_id)` 去重，保证 LangGraph 节点 replay 时不会重复累计结果。

## 7. 任务级 Worktree 与分支

### 7.1 目录结构

每个 Run 继续保留现有集成工作区，同时增加任务工作区：

```text
data/workspaces/<project>-run-12345678/
data/workspaces/<project>-run-12345678-tasks/T1/
data/workspaces/<project>-run-12345678-tasks/T2/
```

### 7.2 分支结构

```text
agent/run-12345678
agent/run-12345678/task-T1
agent/run-12345678/task-T2
```

每一批任务均从该批开始时的 Run 分支 HEAD 创建。Worker 验证通过后在自己的任务分支产生一个提交，Integration 只接收提交 SHA，不读取 Worker 的未提交工作目录。

### 7.3 WorkspaceManager 扩展

新增以下职责：

```python
create_task_workspace(...)
commit_task_workspace(...)
remove_task_workspace(...)
cleanup_batch_workspaces(...)
```

要求：

- 所有路径必须解析为绝对路径并验证位于配置的 workspaces 根目录内。
- 创建前确认源仓库根路径，禁止误用外层 Git 仓库。
- 任务分支名和目录名必须经过安全字符归一化。
- 未集成或发生冲突的任务 worktree 暂时保留，便于诊断和人工处理。

## 8. Coding Worker 改造

Coding SubGraph 改为任务级 Worker：

```text
Receive Task
    → Retrieve Context
    → Explore / Plan / Edit
    → Task Validation
    → Commit Task Branch
    → Return TaskExecutionResult
```

关键约束：

- Session ID 继续包含 `run_id` 和 `task_id`，保证任务间会话隔离。
- 所有文件工具和测试工具使用 Worker 自己的 `workspace_path`。
- Worker 只更新本任务数据库记录和自己的 RuntimeSession。
- Worker 不向共享 Run worktree 写文件。
- Worker 的异常转换为任务结果，不应直接终止其他并行分支。

## 9. Integration 节点

Integration 是并行分支和全局状态之间的唯一写入边界，职责如下：

1. 等待本批所有 Worker 产生终态结果。
2. 校验结果的 `batch_id` 和任务集合。
3. 按任务拓扑顺序处理成功结果，不按 Worker 完成时间处理。
4. 将任务提交依次 cherry-pick 到 Run 分支。
5. 成功集成后将任务标记为 `COMPLETED`。
6. Worker 失败的任务标记为 `FAILED`。
7. 对失败任务的下游执行阻塞传播。
8. 汇总 `changed_files`、`completed_tasks` 和任务结果摘要。
9. 批次完成后运行快速集成验证。
10. 返回 Scheduler 调度下一批任务。

### 9.1 Git 冲突处理

当 cherry-pick 发生冲突时：

1. 立即执行安全的 cherry-pick abort。
2. 已成功集成的前序任务保持不变。
3. 冲突任务保持未完成状态并记录提交 SHA、冲突文件和错误摘要。
4. 将冲突任务送入串行 Repair Worker。
5. Repair 基于当前 Run 分支重新创建工作区并应用原任务意图。
6. 超过 `max_code_retry` 后进入 `needs_human`。

禁止通过覆盖文件或使用 `git reset --hard` 静默处理冲突。

## 10. 文件冲突预防

为 `TaskRecord` 增加可选字段：

```python
target_files: list[str] = []
```

Architect 应尽量给出预计修改范围。Scheduler 在组成批次时避免并行执行 `target_files` 有交集的任务。

该字段只用于调度优化，不能替代 Git 冲突检测，因为 Agent 的实际修改范围可能超出规划。

## 11. 验证与测试策略

### 11.1 Worker 级验证

- 每个 Worker 在自己的 worktree 中运行任务级验证。
- 验证通过后才能创建任务提交。
- 验证失败只触发该任务自己的修复循环。

### 11.2 批次级验证

- Integration 合并本批提交后运行快速验证。
- 批次验证失败时，结合本批提交范围选择串行 Repair 目标。

### 11.3 全局验证

- 所有任务成功集成后运行完整 `test_command`。
- 完整测试通过后才进入 Reviewer。

## 12. HITL 审批与暂停

### 12.1 多审批模型

当前每个 Run 只有一个 `pending_payload`，需要升级为：

```python
pending_approvals: dict[str, dict]
```

每个审批载荷必须包含：

- `approval_id`
- `interrupt_id`
- `run_id`
- `batch_id`
- `task_id`
- `tool`
- `arguments`
- `options`

API 和前端通过 `approval_id` 精确响应审批，禁止后来的审批覆盖先前审批。

### 12.2 分阶段交付

首期建议：

- auto 模式允许并行。
- interactive 模式自动降级为串行。
- 保留所有现有单审批行为。

第二期完成多中断恢复、审批队列和前端多审批面板后，再开启 interactive 并行。

### 12.3 Pause 语义

- 收到 pause 后立即停止分发新批次。
- 活动 Worker 在下一个安全点挂起或完成当前原子工具调用后挂起。
- 所有活动 Worker 到达安全状态后，将 Run 标记为暂停。
- resume 恢复原批次，reject 取消未完成 Worker。
- 取消后清理未集成任务 worktree，保留 Run 集成工作区和事件记录。

## 13. 失败、重试与恢复

### 13.1 任务失败

- 单个任务失败不取消同批其他独立任务。
- 失败任务按现有 `max_code_retry` 单独重试。
- 依赖失败任务的下游任务进入 `BLOCKED`。

### 13.2 非法 DAG 安全停止

- Scheduler 每次调度前重新执行 DAG 校验与拓扑排序，不能只依赖 Architect 的入口校验。
- 从检查点恢复到 Integration 或 Repair 时同样重新校验，防止损坏状态绕过 Scheduler。
- 发现自依赖、循环依赖、重复任务 ID 或缺失依赖时，不分发新的 Coding Worker。
- 节点写入 `needs_human=true`、清空 `ready_tasks`，记录 `invalid_task_dag` 错误事件和具体原因，并通过 `blocked` 路由安全结束 Development SubGraph。

### 13.3 服务重启

Checkpoint 和数据库至少需要持久化：

- 当前 `batch_id`。
- 已分发任务列表。
- 每个任务的 worktree、branch 和 commit SHA。
- Worker 终态结果。
- Integration 已处理到的位置。
- 未完成审批列表。

恢复时遵循幂等规则：

- 已有任务提交不重复调用 LLM。
- 已 cherry-pick 的提交不重复合并。
- reducer 不重复追加同一任务结果。
- 未完成 Worker 从对应 RuntimeSession 恢复。

## 14. 可观测性与前端

新增或扩展事件：

```text
BATCH_SCHEDULED
TASK_WORKSPACE_CREATED
TASK_STARTED
TASK_COMPLETED
TASK_FAILED
INTEGRATION_STARTED
TASK_INTEGRATED
INTEGRATION_CONFLICT
BATCH_COMPLETED
```

前端 TaskDAG 应能同时展示多个 `RUNNING` 任务，执行轨迹按 `task_id` 区分 Coding Worker。现有 `approval_id` 复位语义继续保留，多审批阶段改为按审批项分别复位。

## 16. 实施阶段

### 当前实施状态（2026-10-22）

阶段一已经完成并通过全量后端回归与前端构建验证：

- auto 审批模式下，Scheduler 使用 LangGraph `Send` 对同批 READY 任务进行有界 fan-out。
- 并行 Coding Worker 使用独立 task worktree/branch，只通过幂等 `coding_results` reducer 返回任务级结果。
- Integration barrier 按拓扑顺序 cherry-pick，支持成功、失败、依赖阻塞、冲突回滚和 replay 幂等。
- `parallel_coding_enabled=false` 与 interactive 模式继续使用原串行嵌套 Coding SubGraph，保留工具审批的 interrupt/replay 语义。
- 人工交付批准后创建独立的 delivery marker commit；并行任务提交在隔离的 Run 分支内完成，不会自动 push 或修改用户原始工作区。
- 前端叙事已覆盖批次调度、任务工作区、集成开始、成功、冲突和批次完成事件。

已知分阶段约束：interactive 多 Worker 并行仍未开放；多审批队列、活动批次的完整跨进程恢复、取消时清理所有未集成 worktree，继续归入阶段二/三。

### 阶段一：并行执行基础

- 增加配置和并发状态模型。
- 实现任务级 worktree。
- 实现 Scheduler 动态 fan-out。
- Coding Worker 返回隔离结果。
- 实现 Integration barrier 和确定性合并。
- auto 模式下启用并行，interactive 模式保持串行。

### 阶段二：可靠性

- 完成幂等 reducer。
- 完成批次级 Checkpoint 恢复。
- 增加 Integration 冲突修复。
- 完善取消和 worktree 清理。
- 增加并发资源限制和超时处理。

### 阶段三：完整 HITL 与前端

- 实现多审批队列和基于 `approval_id` 的恢复。
- 支持 interactive 模式并行。
- 更新 TaskDAG、执行轨迹和审批面板。

## 17. 测试计划

至少增加以下测试：

1. 两个无依赖任务的执行时间真实重叠。
2. 同时运行的 Worker 数不超过 `max_parallel_coders`。
3. 下游任务在全部依赖成功集成前不会启动。
4. 每个任务获得不同的 worktree 和 branch。
5. 两个任务修改不同文件时能够自动集成。
6. 两个任务修改相同文件时不会静默覆盖。
7. 单个 Worker 失败时其他独立 Worker 仍可完成。
8. 失败任务的下游被正确标记为 `BLOCKED`。
9. Worker 级重试不会重跑整个批次。
10. Integration 合并顺序稳定且可重复。
11. 节点 replay 不会重复累计结果或重复 cherry-pick。
12. 服务重启后不会重复执行已经提交的 Coding 任务。
13. 多个工具审批不会互相覆盖。
14. pause、resume、reject 在活动批次中行为正确。
15. 关闭并行开关后保持现有串行行为。
16. 全量现有测试继续通过。

## 18. 验收标准

实现完成后必须满足：

- 多个无依赖 READY 任务能够并行运行。
- 并发数始终受配置上限约束。
- Worker 文件系统、Git 分支和 RuntimeSession 完全隔离。
- 并行状态写入不会触发 LangGraph 状态冲突。
- 集成顺序确定，不依赖 Worker 完成先后。
- 同文件修改不会发生静默覆盖。
- 单任务失败不会取消其他独立任务。
- DAG 依赖、失败阻塞和重试语义保持正确。
- Checkpoint 重放不会重复执行已完成副作用。
- 所有挂起审批都具有唯一 `approval_id`。
- 完整集成测试和 Reviewer 仍位于全部任务完成之后。
- 现有串行工作流和测试保持兼容。

## 19. 推荐决策

采用“任务级 worktree + 动态 fan-out + 集中 Integration”的方案，并分阶段交付：

1. 首先完成 auto 模式下的安全并行执行。
2. 随后补齐冲突恢复和服务重启幂等性。
3. 最后实现多审批队列并开放 interactive 并行。

该方案改动范围大于在共享目录中直接使用 `asyncio.gather()`，但能够提供可恢复、可审计且不会静默覆盖代码的并行执行语义。
